Warum AI Coding?

AI Coding kann Hürden reduzieren, aber nur auf einer gesunden Engineering-Basis.

  • Schnellere Exploration und Einarbeitung — weniger wiederkehrender Boilerplate-Code
  • Kein Ersatz für Architektur, Tests, Code Reviews oder Verantwortung
  • Ein KI-Agent verstärkt, was im Repo schon da ist — gut und schlecht -> Testing immer wichtiger

Der Agent ist so gut wie dein Repo, deine Tests und dein Context.

RAI-Leitplanken — Regel #1: Vertraulichkeit

  • Source Code ist mindestens „Intern". Verarbeitet die Anwendung höher klassifizierte Daten, übernehmen Code und Kopien die höchste Klassifizierung.
  • Keine vertraulichen/geheimen Inhalte in externe AI-Tools — nur freigegebene Enterprise-Instanzen und Use Cases.
  • SITAN & AGB vor der Nutzung prüfen: Speicherort, Training, Zugriff.
  • MCP-Server und Agents brauchen explizite Governance.
  • Die menschliche Verantwortung bleibt bei uns — vor jedem Merge.

Konzept 1 von 9

Was ist ein LLM?

Ein Large Language Model ist ein neuronales Netz, trainiert auf riesigen Textmengen. Es sagt jeweils das wahrscheinlichste nächste Token voraus — es „weiss" nichts, es rechnet Wahrscheinlichkeiten.

Beispiel: „Der Himmel ist ___" → Modell schlägt „blau" vor, weil diese Fortsetzung in den Trainingsdaten am häufigsten vorkam.

Für die Praxis wichtig:

  • LLMs sind probabilistisch → gleiche Frage kann leicht unterschiedliche Antworten liefern
  • Trainings-Cutoff: aktuelle Infos müssen als Kontext oder über Tools (MCP) mitgegeben werden
Konzept 2 von 9

Tokens & Context Window

  • Text wird in Tokens zerlegt (grob: 1 Token ≈ 4 Zeichen)
  • Beispiel: „Kontoauszug" → drei Tokens: Kon to auszug
  • Context Window = Kurzzeitgedächtnis des Modells: alles, was es in einer Anfrage „sieht"
  • Ist das Fenster voll, wird älterer Inhalt komprimiert oder vergessen (Compaction)
Praxis-Tipp: Sessions unter ca. 100k Tokens halten — /context, /compact "wichtige Entscheidungen behalten", /clear.
Konzept 3 von 9

Was ist ein AI-Agent? (Agentic Loop)

Assistant chattet nur — Agent handelt: liest Dateien, schreibt Code, führt Befehle aus, wertet Ergebnisse aus.

Prompt → Reasoning → Tool Call → Tool-Ergebnis → (wiederholen) → Antwort
Beispiel: „Füge einen Test für die Zinsberechnung hinzu."
→ Agent liest ZinsService.java → schreibt Test → führt mvn test aus → sieht Fehler → korrigiert → wiederholt, bis grün.

Der Loop läuft autonom — der Mensch setzt das Ziel und prüft das Ergebnis.

Konzept 4 von 9

Prompt-Engineering vs. Context-Engineering

Prompt-Engineering
wie ich frage

„Du bist Senior-Java-Reviewer. Prüfe diesen Diff strikt auf Security-Probleme, priorisiert."

Context-Engineering
was das Modell sehen darf/soll

Regeln einmal in AGENTS.md statt in jedem Prompt neu zu erklären.

Context Engineering schlägt Prompt Engineering — strukturell wichtiger für wiederholbare, gute Ergebnisse.

Konzept 6 von 9

Skills — wiederverwendbare Mini-Prozesse

Ein Skill = ein Ordner mit SKILL.md. Wird automatisch getriggert, wenn seine Beschreibung passt — oder manuell per /skill-name.

---
name: RAI-code-review
description: Prüft Code auf Qualität, Tests, Security.
  Verwenden, wenn ein PR reviewed werden soll.
---
Prüfe: keine Secrets · Tests vorhanden · klare Modulgrenzen.
Berichte nach Priorität: Kritisch / Warnung / Vorschlag.

Drei Typen: Knowledge-, Workflow- und Tool-Skills.

Konzept 7 von 9

Subagents

Ein Subagent hat ein eigenes, isoliertes Context-Fenster. Nur sein Endergebnis fliesst zurück in die Hauptkonversation — spart Tokens, hält den Hauptkontext sauber.

Beispiel: Ein log-analyzer-Subagent liest ein 5.000-Zeilen-Build-Log und meldet nur: „3 Fehler gefunden: NullPointerException in OrderMapper:42. 2 Warnungen."

Einsatzgebiete: Code Review, Log-Analyse, Recherche — parallel zur Hauptaufgabe.

Subagent erstellen

Du kannst Subagents manuell schreiben oder interaktiv erzeugen: `/agent` → Create new agent (Copilot generiert ein interaktives Template).

Beispiel log-analyzer.agent.md:

---
name: log-analyzer
description: Analysiert Build-Logs und Fehlerausgaben. Nutze mich bei Build-Fehlern, langen Log-Dateien oder wenn "logcheck" im Prompt vorkommt.
tools: [read, grep]
---

Du bist ein Log-Analyse-Experte. Lies die angegebene Log-Datei vollständig,
identifiziere alle Fehler und Warnungen, und antworte NUR mit einer kompakten
Zusammenfassung im Format:
"X Fehler gefunden: [Fehlertyp] in [Datei:Zeile]. Y Warnungen."

Gib keine Rohdaten oder Log-Auszüge zurück, nur die Zusammenfassung.
Konzept 8 von 9

Multi-Agent / Orchestrierung

Mehrere (Sub-)Agenten arbeiten parallel oder in Ketten an Teilaufgaben.

Beispiel: Ein „Planner"-Agent zerlegt ein Feature in Tasks → mehrere „Worker"-Agenten implementieren parallel → ein „Reviewer"-Agent prüft alle Diffs.
VorteilRisiko
Höherer Durchsatz, weniger Hand-offsRunaway Agents, verlorene Human-Checkpoints
Konzept 9 von 9

MCP (Model Context Protocol)

Offener Standard von Anthropic: verbindet Agenten mit externen Systemen (GitHub, Jira, Datenbanken, …).

Host (Copilot/Claude) → MCP-Client → MCP-Server → externes System

Beispiel: Ein GitHub-MCP-Server erlaubt dem Agenten, Issues zu lesen und PRs zu erstellen — ohne Custom-Integration.

⚠️ Reales Sicherheitsrisiko (Prompt Injection, Tool-Missbrauch). Nur von RAI freigegebene MCP-Server verwenden.

Risiken & typische Entwickler-Sorgen

  • „Almost right"-Frust — Output sieht plausibel aus, braucht Nacharbeit
  • Debugging-Aufwand — schneller generiert ≠ schneller ausgeliefert
  • Quality Drift — ohne Leitplanken entstehen technische Schulden
  • Data Leakage — Prompts/Logs können geschützte Infos enthalten
  • Kosteneskalation — lange Sessions verbrauchen Tokens

Mitigation: Ask/Plan-Modus starten, Autopilot nur für Low-Risk, Diffs immer reviewen.

Spec-Driven Development — kurz

0. Feature & Datenklassifizierung klären
1. Kleine Spec mit Akzeptanzkriterien schreiben
2. KI nach Rückfragen/Edge-Cases fragen lassen
3. Plan freigeben, bevor Dateien geändert werden
4. In kleinen Schritten implementieren
5. Mit Tests, Review und Security-Checks verifizieren

Loop: Spec → Review → Plan → Implement → Verify

Die Spec überlebt Context-Resets — neue Sessions starten von ihr, nicht vom Chat-Verlauf.

Nächste Schritte

  • AI-Readiness-Score pro Repo erheben
  • AGENTS.md/CLAUDE.md in aktiven Repos anlegen
  • Erstes SKILL.md-Template im Team-Space ablegen
  • Guardrails definieren: Team-Standard für permissions-config.json

Installing Open WebUI with Bundled Ollama Support

Dieses Installationsverfahren nutzt ein einzelnes Container-Image, das Open WebUI mit Ollama bündelt und so eine einfache Inbetriebnahme mit nur einem Befehl ermöglicht. Wähle den passenden Befehl je nach Hardware:

Mit GPU-Unterstützung — nutzt GPU-Ressourcen:

docker run -d -p 3000:8080 --gpus=all -v ollama:/root/.ollama -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:ollama

Nur CPU — wenn keine GPU verfügbar ist:

docker run -d -p 3000:8080 -v ollama:/root/.ollama -v open-webui:/app/backend/data --name open-webui --restart always ghcr.io/open-webui/open-webui:ollama

Beide Befehle installieren Open WebUI und Ollama in einem Rutsch. Nach der Installation erreichst du Open WebUI unter http://localhost:3000.

Was ist RAG?

Generative KI verfügen in der Regel nicht über verlässliche Quellenangaben und sind nicht zwangsläufig aktuell. RAG (Retrieval‑Augmented Generation) kann hier helfen: Ein Retrieval‑System holt relevanten Kontext aus einer Wissensquelle (z. B. hochgeladene Dateien oder eine lokale Datenbank) und stellt ihn dem Modell bereit, sodass Antworten präziser und besser nachvollziehbar werden.

Retrieval-Augmented Generation (RAG) kombiniert eine Wissensquelle (z. B. hochgeladene Dateien oder eine lokale Datenbank) mit einem Sprachmodell: Ein Retrieval-System sucht relevante Informationen aus der Wissensquelle und stellt sie dem Modell als Kontext bereit. Das Modell nutzt diesen Kontext, um präzisere und kontextreichere Antworten zu erzeugen.
